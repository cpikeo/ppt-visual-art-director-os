# 端到端制作效率账（Production Ledger）

`think`/`plan`/缓存命中只是确定性规划层的速度。**从 Brief 到最终成品**的真实成本
还包括：作者执行（落稿）、判断卡的重复读取、修复轮、视觉返工、质量复验。本账把
这些量记下来，并规定：**任何提速宣称必须与质量门同轮配对**（bench 57 + unseen +
selftest 全绿才算提速成立）。

## 追踪字段（每份成品一行）

| 字段 | 定义 |
|---|---|
| 制作时间 | brief 提交 → release strict PASS 的墙钟（含作者落稿） |
| 调用次数 | plan/check/预览渲染等工具往返数 |
| 修复轮数 | check 出 BLOCKED/repair packet 的次数（含被拦下的那次） |
| 重复读取 | 判断卡/骨架/契约的回看次数（作者侧摩擦） |
| 视觉返工 | 为观感（非合规）改动 build 的轮数 |
| 内容返工 | 为让主张可抽取/口径正确而改写文案的轮数 |
| 质量配对 | 同期 bench/unseen/selftest 状态 |

### 对照读法（这才是“端到端提速”的证据形态）

- 同一作者第二单：修复轮 5→1 → **0**、check 往返 5→1、内容返工集中在**判断边界**
  （主张措辞）而非遗漏。速度的实质收益来自**一次做对的比率**，不是 think 的毫秒。
- 两单 brief→PASS 工具往返：deck-A ≈ 12 次，deck-B ≈ 5 次。
- think(30p) 28.68→10.98ms（−61.7%）仍然成立，但它只解释规划层；**上表才是制作层**。

## 之后每份成品怎么记

1. 跑 `plan` 后把 plan 耗时写进第一行；
2. 每次 `check` 无论 PASS/BLOCKED 都计 1 轮，BLOCKED 另计修复轮；
3. 为观感改 build 记视觉返工；为让主张/口径可核对而改文案记内容返工；
4. 收口时必须同轮跑：`bench.py` + `unseen_bench.py` + `python3 -m scripts.selftest`，
   三者状态写进「质量配对」列；**任一不绿，该单不得宣称提速或完成**；
5. 人工视觉验收（acceptance/验收单.md）是另一本账，不签在本账里。

## 判断输出压缩的质量回退检查

本仓对 intelligence 的任何提速/删并（P1 合并共享实现、缓存收口等）都按同一规程：
改前改后跑 57 例 + 泛化套 + selftest 三件套，**泛化套期望冻结哈希不变、结果逐条对照**。
9.30.1 的 `_strip_annotations`/`_locate_numbers` 合并即按此执行：三套全绿、泛化 75/81
六处发现逐字不变（零行为差异实证）。
